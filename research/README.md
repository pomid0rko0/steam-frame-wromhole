# Радикальное ускорение: исследование

Вопрос владельца: кадры не успевают, особенно с движущимися предметами, вблизи глаз и на границе червоточины. Нужно радикально ускорить вычисления, допускаются любые изменения вплоть до переписывания на Rust. Форма горла и вид сцены не фиксированы, Godot не обязателен. Но обходить проблему упрощением формы, сцены или разрешения запрещено.

Здесь: что кадр обязан посчитать, если выводить из самой задачи, что я проверил прототипами (с цифрами и способом их повторить), какую архитектуру предлагаю, что в ней пока только оценка и как её проверить в шлеме.

- **[README]** — замер скоростью в шлеме из README, не мой;

## Коротко

1. **Кривая часть луча считается в каждом пикселе заново, хотя для данного глаза она зависит от одного числа.** По симметрии путь луча в его плоскости определяется углом α между лучом и направлением глаз → центр. Значит, вся кривая геометрия кадра — две таблицы на глаз, по α и по ψ или длине пути, около 1,5·10⁶ чисел, вместо интеграла и отсчётов в каждом из 6·10⁶ пикселей.
   - **[замер]** По таблице 2048×256 на глаз ошибка во всех 10 позах — до 0,10 px для пола и до 0,15 px для неба.
   - Ни одного пикселя не того класса (пол, небо, мир A или B).
   - Включены лучи, огибающие горло, и глаз внутри горла.
2. **Поиск подвижных предметов отсчётами вдоль пути не ограничен по цене.** Модель цены по нынешнему шейдеру (раздел 5.1): мяч в руке дорожает с размером (на краю 10 → 25 → 40 см: +0,6 → +2,9 → +4,0 мс) и на краю (+2,9 мс там, +0,06 у старта). С близостью к глазам рост не подтвердился, а движения шейдер не видит вовсе — «движущиеся» этим не объясняются (раздел 5.1).
   - Путь в R⁴ идёт с единичной скоростью, поэтому хорда не длиннее дуги. Отсюда поиск с жёсткой границей: шаги по расстоянию до предмета вдали, хорды с поправкой на прогиб вблизи.
   - **[замер]** В шести худших сценах: в среднем 7–11 выборок из таблицы на пиксель-кандидат, максимум 22. Ни одного потерянного пикселя, ошибка точки попадания ≤ 0,14 px.
   - Сцены: мяч 25 см в 35 см от глаз на скруглении, мяч 50 см у внешнего края, мяч 70 см в горле при взгляде вбок, рука 4 см, куб у глаз, куб в горле.
3. **Постоянные расходы движка и скриптов.**
   - **[README]** Пустой одноцветный кадр Godot — 0,8 мс; раздельные проходы, без которых не работает фовеация, — ещё +11%.
   - **[замер]** `main._process` на GDScript с летящими мячами и кубами — 1,1–1,4 мс на кадр (медиана), до 2,75 мс в пике. Облачный Xeon, без рук и XR: это только порядок величины. Цену на шлеме покажут строки опоздавших кадров в его логе (`cpu ... ms render`, `... ms process`).
   - **[замер]** С лежащими предметами столько же, сколько с летящими (1,27–1,31 против 1,20–1,29 мс): процессор «движущиеся» тоже не объясняет.
4. **Предложение** — новое ядро:
   - таблицы на глаз строятся каждый кадр на GPU (compute) для любого сферически симметричного профиля;
   - на пиксель — несколько выборок из таблиц и плоская трассировка;
   - предметы — ограниченный поиск;
   - худший кадр ограничен по построению, а не в среднем.
   
   Дальше — свой движок на Rust (OpenXR + Vulkan напрямую): физика в нативном коде, один проход рендера прямо в картинку шлема, своя фовеация лучами вместо плиток драйвера. Порядок шагов — в разделе 8: сначала замер в шлеме, потом переписывание.
5. **Чего я не знаю.** Время на GPU шлема. Модель цены для шейдеров с предметами ошибается в 1,8 раза, а сколько на Adreno 750 стоит выборка из таблицы RGBA32F, я не знаю. Оценки в разделе 6 — арифметика, решать по ним нельзя. Первые шаги плана — замеры в шлеме: сборка, лог, ответ «да или нет».

## 1. Задача

Показать в Steam Frame, автономно, в стерео, вид из 3D-гиперповерхности в R⁴, по которой идёт свет по геодезическим. Сейчас это `union_round(плоскости w = ±h, сфера ρ₀ вдоль w, R)`, но форма может быть любой.

Требования:
- стерео точное;
- картинка совпадает с геодезическими до долей пикселя;
- **ни одного опоздавшего кадра** на 120–144 Гц в худшем случае — один поздний кадр сбрасывает SteamVR на половинную частоту на секунды [README];
- подвижные мячи и кубы с физикой, руки.

Железо: Adreno 750, Snapdragon 8 Gen 3, SteamVR; приложению — 1728² на глаз.

Из требования про худший кадр следует главное правило: **цена кадра не должна зависеть от того, где предметы и куда смотришь**. Средняя цена мало что говорит.

## 2. Что кадр обязан посчитать

### 2.1 Кривая часть луча — функция одного угла

Метрика `ds² = dl² + r(l)² dΩ²` сферически симметрична. Повороты вокруг оси «глаз — центр» — изометрии, которые оставляют глаз на месте. Поэтому луч из глаза лежит в плоскости через центр, и **его путь в своей плоскости зависит только от угла α между лучом и радиальным направлением**. Пиксель отличается от соседа поворотом этой плоскости (угол β), а не самим путём.

Что нужно пикселю из кривой части, и всё это функции α или (α, ещё одно число):
- **выход из оболочки:** угол поворота ψ_exit, длина пути, в какой мир выходит — функции α;
- **пол:** экваториальная поверхность, в плоскости луча это прямая через центр. Пиксель знает её угол ψ_F по своему β (один `atan2`), а точка пола — `l(α, ψ_F)` из 2D-таблицы;
- **предметы:** точка пути в R⁴ в координатах плоскости луча, `(r cos ψ, r sin ψ, w)` как функция (α, s), где s — длина пути, — 2D-таблица.

Таблицы строятся на каждый глаз каждый кадр. Строка таблицы — один луч, проинтегрированный ODE геодезической, поэтому годится **любой** сферически симметричный профиль r(l): крутилки формы горла бесплатны. Для несимметричных форм (тор, произвольный SDF) этого сведения нет — раздел 7.

Особенность — лучи около критического угла α_c (b = r_min), которые огибают горло. Переход «ушёл / ещё кружит» там экспоненциально узок по α. Равномерная сетка по α это не берёт: до 1,8 px ошибки **[замер]**. Сетка, логарифмически сгущённая к α_c (в пикселе это один лишний `log`), берёт: 0,065 px.

### 2.2 Предметы: поиск с жёсткой границей цены

Предмет — мяч (хордовое расстояние в R⁴ меньше радиуса) или 4D-коробка, как в SDF-сцене из видео. Луч проходит по поверхности с единичной скоростью в R⁴: |Q(s₁) − Q(s₂)| ≤ |s₁ − s₂|. Отсюда метод:
- **далеко** (расстояние d ≥ размера): шаг на d вдоль пути безопасен, это sphere tracing, но по самому пути;
- **близко:** хорды длиной в полразмера. Каждая точно проверяется против предмета, раздутого на прогиб хорды `K·Δs²/8`, где K — наибольшая главная кривизна пространства (здесь 1/R = 1 м⁻¹). Хорда, которая задела раздутый предмет, делится пополам до трёх раз (прогиб падает вчетверо на уровень). Найденный вход уточняется методом regula falsi.

Число шагов ограничено геометрией и, кроме того, жёстким пределом цикла (24): даже в патологической сцене кадр не может стать дороже, чем «все кандидаты × 24 выборки». Первая версия без деления хорд теряла пиксели, где луч срезает ребро куба: расстояние до коробки там с изломом, и минимум по 4 отсчётам его не видел, до 3,9 px **[замер]**. Деление хорд это исправило.

### 2.3 Остальное

- **Пиксели.** Фовеация по взгляду сейчас — плитки драйвера, 6×3 зоны на глаз [README]. Трассировщику плитки не нужны: свой проход может пускать лучи с любой плотностью, плавно падающей от взгляда. Сколько это даст и не будет ли мерцания на краях, проверено только в литературе (kernel/log-polar foveated rendering), не здесь.
- **Постоянные расходы.** Пустой кадр Godot 0,8 мс, раздельные проходы +11% [README]. Нативный рендер — один проход в картинку шлема. Сколько он стоит на Frame, не знаю: это первый замер плана.
- **CPU.** Физика 14 тел в кривом пространстве в нативном коде — порядка десятков микросекунд (ожидание, не замер). В GDScript весь `main._process` — 1,1–2,75 мс **[замер, Xeon]**.

## 3. Эталон

`research/geo`, Rust, float64. Геометрия выведена из определения SDF заново, код `ref/` не используется. RK4 по длине пути на скруглениях, цилиндр и плоские части — в замкнутом виде, события (вход в цилиндр, выход из оболочки, заданные ψ) — делением шага.
- Сходимость: шаг в 4 раза мельче меняет ответ меньше чем на 10⁻⁴ px **[замер]**.
- Независимая сверка: полный угол поворота в оболочке против квадратуры scipy ∫ b dl / (r√(r² − b²)) для 9 прицельных параметров, в том числе b = 2,99 и 3,01 у критического 3,0. Расхождение ≤ 7·10⁻¹² рад (`results/sweep.txt`) **[замер]**.

## 5. Прототип 2: подвижные предметы

Шесть сцен, выбранных как худшие из жалоб: близко к глазам, на краю, в горле. Предмет ставится геодезической из глаза. Пиксели берутся вокруг изображения предмета и по всему полю зрения.
- Кандидат — пиксель, чья плоскость луча проходит ближе размера предмета от его центра.
- Эталон — путь с отсчётами через 0,5 мм и деление пополам.
- «Потерян» — эталон попал, метод нет. «Ложный» — наоборот.

### 5.1 Проверка: от чего дорожает нынешний шейдер с предметами

Модель цены (`tools/adreno_cost.sh --toys --held --split`) по нынешнему шейдеру с руками и мячом в правой руке. Расстояние — от руки, вдоль её оси; взгляд на 20° вниз; без фовеации; мс на кадр. Для шейдера с предметами модель занижает примерно в 1,8 раза [README], поэтому смотреть надо на разницы, а не на сами числа **[замер модели]**:

| мяч в руке | старт | снаружи у края | на краю, на горло | на краю, вбок | горло, вбок |
|---|---|---|---|---|---|
| нет (только руки) | 3,09 | 6,05 | 4,86 | 5,46 | 4,08 |
| 25 см, в 0,6 м | 3,07 | 6,55 | 7,29 | 5,98 | 4,40 |
| 25 см, в 0,3 м | 3,15 | 6,48 | 7,73 | 6,19 | 4,55 |
| 25 см, в 0,15 м | 3,36 | 5,79 | 6,68 | 6,59 | 4,83 |
| 10 см, в 0,3 м | 3,10 | 6,03 | 5,47 | 5,80 | 4,29 |
| 40 см, в 0,3 м | 3,33 | 5,76 | 8,85 | 7,11 | 5,15 |

- **Размер** — да.
- **Край** — да: тот же мяч добавляет +2,9 мс на краю и +0,06 у старта.
- **Близость к глазам** — нет. На краю мяч в 0,15 м дешевле, чем в 0,3 м: видимо, он заслоняет вид, и лучи на нём кончаются.
- **Движение** — шейдер его не видит. Загрузка униформ и заглушек трафарета идёт каждый кадр, движутся предметы или нет, а скрипты стоят столько же (раздел «Коротко», п. 3).

Что тогда за «особенно на движущихся», не установлено. Кандидаты:
- места, где предметы бывают только в движении: мяч в воздухе в горле. В README есть непроверенная запись: в игре у горла кадры по 8,5 мс, а в туре замера на том же месте с лежащими предметами — 3,5–4 мс;
- то, чего здесь не воспроизвести: настоящий XR-кадр с руками, рендер-поток, SteamVR.

Решит лог шлема. Строки опоздавших кадров там уже есть, но без положения предметов. Следующая сборка должна писать в них, где каждый мяч, куб и рука.

## 6. Сколько это может дать — оценка, не замер

Веса модели цены, подогнанные по шлему на шейдерах без предметов: мс на кадр (оба глаза, 1728², без фовеации) за одну команду на каждую волну кадра:
- 1,61·10⁻³ — такт АЛУ;
- 1,05·10⁻³ — `nop`;
- 0,0258 — трансцендентная команда;
- 0,146 — команда текстурного блока.

Вес выборки подогнан на экранных производных. Сколько стоит выборка RGBA32F из массива текстур, неизвестно — отсюда вилка ниже.

- **Одна выборка пути на весь кадр** ≈ 0,10 мс без учёта текстурного блока, 0,25 мс с ним.
- **Мяч у глаз** (кандидаты ~⅓ кадра, ~10 выборок): +0,3…0,8 мс без фовеации, +0,1…0,3 мс со своей узкой (33% лучей).
  - Сейчас по модели та же сцена у края — 7,7 мс против 4,25 мс без мяча [README].
  - В шлеме — отдельные кадры до 8 мс на 120 Гц [README].
  - Главное отличие: новая цена не растёт, когда предмет ближе, больше или у края.
- **Кривая часть пола и неба:** грубо ~40 АЛУ, ~30 `nop`, 4 трансцендентные, 2 выборки на пиксель (счёт по прототипу на глаз, не по компилятору) ≈ 0,2…0,5 мс на кадр, если весь кадр кривой. Сейчас лучи сквозь кривую зону у края стоили ~1,3 мс до последних ускорений [README]. Выигрыш здесь умеренный; главное, что цена одинакова в любой позе.
- **Движок:** из 0,8 мс пустого кадра Godot и +11% за раздельные проходы часть уйдёт при одном нативном проходе. Сколько — неизвестно, это замер 2 плана.
- **CPU:** 1–3 мс скриптов на кадр → десятки микросекунд в нативном коде. Это ожидание, не замер: физику на Rust я не переносил.

Итог оценки: худший кадр с предметами — в разы дешевле, обычный — на десятки процентов. Цифры по модели, которая для шейдеров с предметами ошибается в 1,8 раза. Решать по ним нельзя, только по замеру в шлеме.

## 7. Что отброшено и почему

- **Растеризация предметов через уравнение линзы** (вершины переводятся в направления, под которыми их видно). Предмет за горлом даёт кольцо Эйнштейна, у складок изображения сливаются. Треугольники через каустику рвутся, и это как раз у границы. Трассировка с ограниченным поиском работает в любой позе.
- **Перепроекция, ASW, кадры через раз.** Не ускоряет счёт, а в VR это видимые артефакты; что умеет SteamVR на Frame, неизвестно.
- **Аппаратная трассировка лучей Adreno.** Наши примитивы аналитические, BVH им не нужен. Пригодилась бы для произвольных мешей в кривом пространстве, но не для скорости.
- **Профиль с геодезическими в элементарных функциях** (конусы, цилиндры). Это смена формы ради скорости — запрещено. К тому же таблицы на глаз делают форму безразличной для цены пикселя.
- **Ниже разрешение, проще сцена.** Запрещено.
- **Несимметричные формы** (тор, произвольный 4D SDF). Сведения к одному углу нет: луч надо вести численно, и это отдельная задача. Там помогут ограниченный поиск по пути (тот же принцип: хорда ≤ дуги), лучи только там, где путь кривой, и фовеация лучами. Таблицы — нет.

## 8. План

Каждый шаг даёт замер в шлеме. Владельцу — простое «запусти, через пару минут выйди, пришли лог». Переписывать движок до шагов 1–2 нельзя: неизвестно, сколько он сам стоит.

1. **Ядро на таблицах внутри нынешнего приложения**, вариант для замера скорости (13 мест, A/B с нынешним).
   - Таблицы на глаз строит compute-шейдер Godot (RenderingDevice в CompositorEffect, текстуры через Texture2DArrayRD).
   - Отдельно в той же сборке — вариант «N выборок таблицы на пиксель»: сколько на Frame стоит выборка RGBA32F и RGBA16F.
   - Проверки до шлема: `test_stereo.sh` (лучи те же, стерео то же по построению) и сверка картинки с нынешним (`emu_dump.gd`, до 1/255 вне линий сетки).
2. **Пустой кадр своего движка.** Минимальное приложение на Rust: `openxr` + `ash`, multiview, один проход в картинку шлема, карта плотности. Пишет в лог время GPU одноцветного кадра и кадра с ядром из шага 1. Это ответ, сколько из 0,8 мс + 11% — цена Godot.
3. **По результатам 1–2:**
   - если движок стоит заметную долю кадра — переход на свой (OpenXR и ввод, меню, текст, физика на Rust в f64, тесты стерео против растеризации по матрицам OpenXR);
   - если нет — физика в Rust через GDExtension (godot-rust), остальное в Godot.
4. **Фовеация лучами** (нужен свой проход или compute): лучи с плавно падающей от взгляда плотностью, без плиток. Замер — тот же A/B, проверка на глаз — да или нет: «видна ли граница или мерцание по краям».
5. **Предохранитель худшего кадра.** Цена кадра теперь ограничена по построению и предсказуема по позе и предметам. Если предсказание подходит к бюджету, кадр заранее рисуется с более грубой картой периферии, а не опаздывает.

## 9. Как повторить

```bash
cd research/geo && cargo build --release
```
```bash
research/geo/target/release/geo 2048 256 10000 0      # таблицы пола и неба: строки, столбцы, пикселей, бит веса (0 — точно)
```
```bash
UNIFORM=1 research/geo/target/release/geo 2048 256 10000 0   # то же с равномерной сеткой по α
```
```bash
SELFCHECK=1 research/geo/target/release/geo 64 16 1500 0    # эталон против шага в 4 раза мельче
```
```bash
SWEEP=1 research/geo/target/release/geo                     # углы поворота для сверки с квадратурой
```
```bash
research/geo/target/release/toys                            # предметы по точному пути
```
```bash
TABLE=1 TN=512 TS=256 research/geo/target/release/toys      # предметы по таблице (TN строк на сторону, TS столбцов)
```
